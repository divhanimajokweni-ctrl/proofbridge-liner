# ADR 0002: Merkle Mountain Range over Merkle Tree or Other Structures

## Status

Accepted

## Context

The VVU Earth Tech Ledger requires a cryptographic data structure that provides:

1. **Append-only** — New entries are added without modifying existing data
2. **Efficient inclusion proofs** — Prove that a specific entry exists in the ledger
3. **Efficient consistency proofs** — Prove that the ledger at an earlier state is a prefix of the current state
4. **Compact root** — A single hash that commits to the entire ledger state
5. **Efficient updates** — Adding a new entry should be O(log n) or better

The data structure must support:

- Generating inclusion proofs for any entry in O(log n) time
- Generating consistency proofs between any two states in O(log n) time
- Verifying proofs in O(log n) time
- Computing the root hash in O(log n) time after each append

### Candidate Structures

| Structure | Append | Inclusion Proof | Consistency Proof | Root Update |
|-----------|--------|-----------------|-------------------|-------------|
| Merkle Tree | O(n) rebuild | O(log n) | O(log n) | O(n) rebuild |
| Merkle Tree (persistent) | O(log n) | O(log n) | O(log n) | O(log n) |
| Merkle Mountain Range | O(log n) | O(log n) | O(log n) | O(log n) |
| Verifiable Log (CT) | O(log n) | O(log n) | O(log n) | O(log n) |

## Decision

We adopt the **Merkle Mountain Range (MMR)** as the cryptographic indexing structure for the VVU Earth Tech Ledger.

The MMR is a forest of perfect binary trees (mountains). Leaves are appended sequentially and the root is computed by *bagging* all peaks. The implementation follows the specification from the Grin project.

### Key Design Properties

1. **Peak discovery** — Peaks are discovered by decomposing the leaf count into powers of 2 (from largest to smallest). For example, 7 leaves = 4 + 2 + 1 → 3 peaks at heights 2, 1, 0.

2. **Bagging order** — The root is computed by iteratively hashing peak pairs from right to left under the `VVU:MMR:BAG:1:` domain.

3. **Node hashing** — Leaf nodes use `domain_hash(VVU:MMR:INT:1:, 0x00 + data)` and branch nodes use `domain_hash(VVU:MMR:INT:1:, 0x01 + left + right)`. The prefix bytes prevent second preimage attacks.

4. **Position numbering** — Nodes are numbered in post-order traversal, so a parent's position is always greater than its children's positions.

5. **Domain separation** — The MMR uses two distinct domains: `VVU:MMR:INT:1:` for internal node hashing and `VVU:MMR:BAG:1:` for peak bagging. This prevents collision between internal and bagging hashes.

## Consequences

### Positive

- **Efficient append** — O(log n) amortized for each append (most appends are O(1))
- **Efficient proofs** — Inclusion and consistency proofs are O(log n) in size and verification time
- **Append-only** — No need to rebuild or rebalance the tree; existing nodes are never modified
- **Compact root** — A single 32-byte hash commits to the entire ledger state
- **Proven design** — MMR is used in production systems (Grin, Arrow, Polkadot)
- **Simple implementation** — The MMR can be implemented with a dictionary of position → hash

### Negative

- **Non-standard** — MMR is less well-known than Merkle trees; fewer reference implementations
- **Peak bagging** — The root computation is more complex than a simple Merkle tree root
- **Proof size** — MMR proofs include all peaks, which adds overhead compared to a single-root Merkle tree
- **No built-in persistence** — The MMR must be serialized to and from the database

### Neutral

- **Post-order numbering** — The position numbering scheme is unusual but well-defined
- **Multiple peaks** — An MMR with n leaves has O(log n) peaks, which is a property of the structure

## Alternatives Considered

### 1. Traditional Merkle Tree

A balanced binary Merkle tree where each leaf is a ledger entry.

**Rejected because:**
- Not append-only: adding a new entry requires rebuilding the tree
- Rebalancing is complex and potentially non-deterministic
- Not suitable for growing datasets where entries are appended sequentially

### 2. Persistent Merkle Tree

A copy-on-write Merkle tree that preserves old versions.

**Rejected because:**
- Higher memory and storage overhead (old versions must be retained)
- More complex implementation
- Not as well-suited for append-only workloads as MMR

### 3. Certificate Transparency Log

A Verifiable Log structure as used in Certificate Transparency (RFC 6962).

**Rejected because:**
- Designed for a specific use case (certificate transparency)
- The Merkle tree used in CT is a binary hash tree with specific leaf/branch hashing
- Less flexible than MMR for general-purpose append-only logs

### 4. Patricia Merkle Tree

A Merkle Patricia Tree as used in Ethereum.

**Rejected because:**
- Designed for key-value storage, not append-only logs
- More complex than MMR
- Not necessary for sequential entry indexing

### 5. Simple Hash Chain (no tree)

A simple hash chain where each entry's hash is computed from the previous entry's hash.

**Rejected because:**
- No efficient inclusion proofs (must scan the entire chain)
- No consistency proofs (cannot prove prefix relationship)
- Verification is O(n) for all operations
