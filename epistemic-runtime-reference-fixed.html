Chapter 01
Executive Overview
Why the Epistemic Runtime exists, what it solves, and who it serves
The Epistemic Runtime is a production-grade control plane for managing distributed state with mathematical guarantees. In an era where financial systems, healthcare infrastructure, and regulatory frameworks demand provable correctness — not just best-effort consistency — the Epistemic Runtime provides a fundamentally new approach: every state transition is governed by compiled invariant rules, verified through zero-knowledge proofs, and reconciled across organizations via cryptographic Merkle forests.
Traditional distributed systems rely on eventual consistency and manual reconciliation. When violations occur, engineers scramble to diagnose and patch. The Epistemic Runtime inverts this paradigm: invariants are first-class citizens compiled from declarative policy files (.epd), violations trigger automatic self-repair through least-divergent merge proposals, and the entire proof chain is anchored to a tamper-evident Merkle Mountain Range (MMR) log with optional ZK-STARK proofs for privacy-preserving verification.
Core Value Proposition
The Epistemic Runtime transforms “hope it works” into “prove it works.” Every policy, every shard, every merge, and every cross-organization reconciliation carries a cryptographic proof that can be independently verified without trusting the runtime itself.

Chapter 03
The .epd Policy DSL
Declarative invariant specification from human-readable rules to compiled enforcers
The Epistemic Policy Definition (.epd) language is the primary interface for defining system invariants. Rather than writing imperative validation code, policy authors declare what must be true about the system state. The runtime handles how to enforce those constraints, including automatic repair when violations are detected.
// Example .epd policy for a financial settlement system policy SettlementGuarantees { domain = "settlement.vvu.eth" version = "2.3" // Balance integrity: debits must equal credits invariant BalanceIntegrity { predicate: sum(debits) == sum(credits) severity: critical } // Settlement latency must not exceed SLA invariant SettlementLatency { predicate: latency_ms <= 5000 severity: high soft: true } // Cross-shard consistency guarantee invariant CrossShardConsistency { predicate: shard_roots_agree(global_root) severity: critical } shard { strategy: range key: settlement_id } repair { strategy: least_divergent max_iterations: 5 } proof { kind: zk-stark shadow: enabled } }
The .epd DSL provides several key features: Domain isolation ensures policies are scoped to specific business contexts; Severity classification (critical, high, medium, low) determines the runtime's response when violations occur; Soft invariants trigger warnings without halting execution; Shard strategies (range, hash, region) control how state is partitioned across the DAG; Repair strategies define how the self-healing system resolves violations; and Proof configuration specifies whether ZK proofs, MMR proofs, or shadow verification is required.
The compilation pipeline transforms .epd source through four stages: Tokenization (lexer produces typed tokens), AST Construction (parser builds a typed abstract syntax tree), Validation (semantic analysis checks for duplicate names, invalid predicates, and circular dependencies), and Code Generation (produces a RuleSet with executable enforcement functions). The full source for this pipeline lives in src/lib/epd/ with tokenizer.ts, parser.ts, ast.ts, validator.ts, and index.ts.

DAG Topology & Shard Management
Invariant-aware sharding of the state space across distributed nodes
The Epistemic Runtime organizes state as a Directed Acyclic Graph (DAG) where each node represents a shard owning a subset of the state space. Sharding is not merely a performance optimization — it is an invariant-aware partitioning strategy that ensures related invariants are co-located, minimizing cross-shard violations while maximizing parallel execution.

Chapter 05
Self-Repairing Merges
Least-divergent correction with AI-mined invariants and automatic conflict resolution
When an invariant violation is detected, the Epistemic Runtime does not merely alert — it autonomously proposes a repair. The merge reconciliation system generates a MergeProposal that represents the minimum-change correction to restore all violated invariants. This is fundamentally different from traditional error handling: instead of rolling back to a checkpoint, the runtime computes a least-divergent state that satisfies all constraints while preserving as much of the proposed change as possible.
The merge algorithm works in iterative rounds. In each round, it: (1) identifies which invariants are currently violated in the proposed state; (2) computes the minimal delta needed to satisfy each violated invariant; (3) applies deltas in priority order (critical first, then high, medium, low); (4) re-evaluates all invariants to check for cascading violations introduced by the repairs; and (5) repeats until either all invariants pass or the maximum iteration count is reached. The divergence field on each MergeProposal quantifies how far the repaired state deviates from the originally proposed state — a divergence of 0 indicates a perfect merge with no compromises.

AI-Mined Invariants
Beyond hand-authored .epd invariants, the runtime includes an Invariant Miner that analyzes historical state transitions to discover statistically significant patterns. Mined invariants carry a confidence score and are proposed as candidates for promotion to enforced status. This creates a virtuous cycle: the more the system operates, the more invariants it discovers, and the more robust the enforcement becomes.
Chapter 06
Zero-Knowledge Proofs & MMR Ancestry
Privacy-preserving verification and tamper-evident proof accumulators
The cryptographic backbone of the Epistemic Runtime combines Merkle Mountain Range (MMR) accumulators with Zero-Knowledge Succinct Transparent Arguments of Knowledge (ZK-STARKs). MMR provides an efficient, append-only data structure for maintaining a tamper-evident log of all state transitions. ZK-STARKs enable verification of these transitions without revealing the underlying state data — crucial for regulated industries where business logic must remain confidential even during audit.
Each AncestryProof record contains: a proofPath (the sequence of sibling hashes needed to verify inclusion in the MMR), an optional zkProof (the STARK proof that the transition was valid without revealing the state), an anchor field (rekor, blockchain, or transparency_log) for external timestamping, and a shardKey identifying which shard this proof covers. The proof chain forms an append-only log where each proof references the previous one, creating a cryptographically linked sequence that cannot be retroactively altered.
Regulatory Significance
ZK-STARK proofs are transparent — they require no trusted setup ceremony, unlike ZK-SNARKs. This eliminates a key regulatory concern: the possibility that a compromised setup could allow undetectable proof forgery. STARKs also provide post-quantum security, making the proof chain resistant to future quantum computing attacks.
The ZK Circuit section of the dashboard visualizes the SNARK constraints for each policy, showing which invariants have been compiled into arithmetic circuits, their constraint counts, and verification status. Circuit compilation transforms each .epd invariant into a set of polynomial constraints over a finite field. The verifier checks that these constraints are satisfied without learning the witness (the actual state values). Current system metrics show 7 out of 16 proofs (43.8%) have ZK coverage, with the remaining using MMR proofs only.
Chapter 07
Shadow Bridge & Digital Twins
What-if branching, divergence monitoring, and authoritative takeover
The Shadow Bridge enables zero-risk policy testing by running a parallel “shadow” instance alongside the live system. When a new policy or configuration is proposed, the shadow bridge diverts a copy of live traffic to the shadow instance, which processes it under the new rules. The divergence between live and shadow responses is measured in real-time, providing immediate feedback on the impact of proposed changes.
Shadow events come in five kinds: whatif (hypothetical exploration), replay (reprocessing historical events under new rules), divergence (automatic detection of live/shadow disagreements), takeover (promoting shadow to authoritative), and handback (reverting takeover). Each event records both the live state and shadow state as JSON, along with a computed divergence score. The dashboard visualizes divergence trends over time, with configurable alerting thresholds.
For financial institutions, the Shadow Bridge provides a regulator-friendly approach to change management: instead of “deploy and pray,” every configuration change can be validated against live traffic before promotion. For engineers, it eliminates the need for complex staging environments — the shadow IS the staging environment, but it receives real traffic, making its results far more representative than synthetic test suites.
Chapter 08
Trust Runtime Dashboard
Real-time confidence scoring, Bayesian inference, and verification gates
The Trust Runtime Dashboard is the newest addition to the Epistemic Runtime (v0.7), providing a quantified trust framework that translates complex cryptographic and invariant data into actionable intelligence. Rather than requiring stakeholders to interpret raw proof chains and violation logs, the Trust Runtime computes a holistic confidence score with three labeled states: SAFE (≥80%), WARNING (50-80%), and TRIP (<50%).
Confidence Formula
Confidence = (ZK_Proofs / Total_Proofs) × (1 − Violations / Total_Shards)

This formula balances two critical factors: proof coverage (how much of the system's history is cryptographically verified) and violation density (how much of the current state fails invariant checks). A system with high ZK coverage but many violations will score lower than one with moderate coverage but few violations.
The Bayesian Likelihood Engine computes three values for every measurement cycle: Prior (the historical merge success rate, representing our baseline belief), Likelihood (derived from the exponential decay of average divergence — lower divergence means merges are more likely to succeed), and Posterior (the Bayesian update combining prior belief with observed evidence). The delta between posterior and prior reveals how much the latest evidence has shifted our confidence.
Bayesian Update Formula
P(success | evidence) = (likelihood × prior) / (likelihood × prior + (1 − likelihood) × (1 − prior))

Where likelihood = exp(−avg_divergence). This creates a self-calibrating trust score: as the system repairs more violations and generates more ZK proofs, the posterior naturally increases. Conversely, degraded performance causes rapid confidence reduction — the TRIP threshold triggers immediate attention.
The dashboard also includes six Verification Gates representing the deployment pipeline stages: Schema Validation, Invariant Compilation, ZK Proof Generation, Shard Distribution, Shadow Bridge Sync, and Merge & Repair Check. Each gate passes or fails based on real system data, providing a clear deployment readiness signal. The Posterior Distribution panel renders a Gaussian bell curve around the current posterior, showing the probability density of the trust score and enabling risk officers to assess confidence intervals.

Multi-Organization Federation
Cross-organizational verifiable state reconciliation via epistemic:// protocol
The Epistemic Runtime supports multi-organization federation through the epistemic:// protocol, enabling independent organizations to share verified state without exposing internal data. Federation works by exchanging MMR roots and ZK proofs: each organization maintains its own proof chain, and cross-organization consistency is verified by comparing MMR roots at shared boundaries.
The federation model addresses a fundamental challenge in multi-party systems: how can Organization A trust Organization B's state without seeing B's private data? The answer lies in ZK proofs: B can prove that its state satisfies agreed-upon invariants without revealing the state itself. The Federation dashboard section shows bridge connections between organizations, synchronization status, and divergence metrics. Current metrics show 3 federated organizations with 2 active bridges achieving 98% synchronization.
For regulators, federation provides a powerful tool: instead of auditing each organization independently, regulators can verify the consistency of the entire federated system by checking that all MMR roots agree at designated epoch boundaries. Any discrepancy indicates a potential compliance violation that warrants investigation. For fintech companies, federation enables real-time settlement netting across organizational boundaries without a central clearinghouse — the cryptographic proofs serve as the trust anchor.

GitOps Deployment Pipeline
Argo CD App-of-Apps, sync waves, and verification gates for production deployment
The Epistemic Runtime deploys via a GitOps pipeline built on Argo CD's App-of-Apps pattern. This means the entire infrastructure is defined as code in a Git repository, and Argo CD continuously reconciles the live cluster state with the desired state in Git. There are no manual deployments — every change goes through the same automated pipeline with built-in verification gates.

The pipeline uses sync waves to ensure correct ordering: infrastructure components (namespaces, secrets, messaging, databases) deploy first (waves -5 through -1), followed by the runtime core (wave 0), workers (wave 1), a verification job (wave 2), the projector (wave 3), and monitoring (wave 4). The Verification Job at wave 2 is a BUILD GATE — it blocks downstream deployments if the runtime fails its self-checks, ensuring that no broken version reaches the projector or monitoring layers.
The bootstrap script (scripts/bootstrap.sh) handles initial cluster setup, and an ApplicationSet manages multi-environment deployments (production, staging, development) from a single Git repository. Prometheus alerting rules trigger on verification failures, runtime downtime, and high latency, providing 24/7 operational visibility.

Autonomous Task Execution & Agent Development
Building intelligent agents that operate within the Epistemic Runtime
The Epistemic Runtime is designed as a foundation for autonomous agents — software systems that make decisions and execute actions independently, but within provably safe boundaries. The invariant enforcement system acts as a guardrail: no matter what an agent attempts, the runtime will reject any state transition that violates compiled invariants, and will automatically repair any violations through the self-healing merge system.
To develop an agent for the Epistemic Runtime, follow this architecture: (1) Perception — connect to the API endpoints (/api/stats, /api/metrics, /api/trust-runtime) to observe the current system state; (2) Reasoning — use the Bayesian Trust Dashboard data to assess whether actions are safe, computing expected posterior changes before acting; (3) Action — propose state transitions through the merge proposal system, which the runtime validates and potentially auto-repairs; (4) Learning — feed observations into the Invariant Miner to discover new invariants that improve system robustness over time.
// Agent integration pattern const trustState = await fetch('/api/trust-runtime') .then(r => r.json()); // Check confidence before acting if (trustState.confidence.label === 'TRIP') { // Confidence too low — enter safe mode await enterSafeMode(trustState.confidence.explanation); } else if (trustState.likelihood.posterior > 0.7) { // High confidence — proceed with action await proposeStateTransition(action); } else { // Moderate confidence — request human approval await requestApproval(action, trustState); }
Safety Guarantee
Agents operate within a “safe sandbox”: the invariant enforcement system ensures that no agent action can corrupt system state. Even a malfunctioning agent can only propose invalid transitions — the runtime will reject or auto-repair them. This enables high-frequency autonomous operation without human oversight, while maintaining mathematical safety guarantees.

VVU Design System
Visual constitution, token system, and interactive patterns
The Epistemic Runtime dashboard implements the VVU (Verified Verifiable Universe) Design System, a custom visual constitution built on Tailwind CSS with oklch color space. The design system defines four semantic status colors: verified (green, for healthy/compliant states), repairing (amber, for in-progress corrections), violating (red, for active violations), and quarantined (muted, for isolated states). These colors are defined as CSS custom properties using oklch for perceptual uniformity across light and dark themes.

The VVU brand tokens include Crimson (#C41E3A) for critical alerts and border accents, Gold (#C9A84C) for verified status and primary actions, and Near-Void (#09090f) as the base dark background. Typography follows a three-family system: Syne for display headings (geometric, futuristic), IBM Plex Mono for data and code (technical precision), and DM Sans for body text (readable, approachable). Gradient border cards (GradientBorderCard) provide visual hierarchy through subtle oklch gradients. The bg-grid-fine CSS class adds a fine grid pattern as a background texture. The animate-epistemic-pulse animation provides a breathing effect for status indicators. The glow-verified utility adds a subtle green shadow to key UI elements. Together, these primitives create a distinctive visual language that communicates system status at a glance.
